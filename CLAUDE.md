# Lift App (ELS) — правила работы Claude Code

## Контекст проекта
- **Проект**: «Единая лифтовая система» — моно-репозиторий: REST API + фронтенд.
- **Раскладка**: `backend/` (FastAPI), `frontend/` (Flutter), `infra/` (docker compose),
  `els-vault/` (база знаний), `docs/`, `scripts/` (инструменты репо).
- **Стек бэка**: FastAPI, SQLAlchemy 1.4, Alembic, PostgreSQL, JWT (python-jose), uv/uvicorn, Ruff
- **Стек фронта**: Flutter (Dart), сборки android/ios/web, flutter_bloc + provider, dio.
  Код унаследован от прежнего подрядчика, качество низкое — см.
  `els-vault/archive/состояние/аудит фронта на 2026-08-11 - Flutter, 71 тысяча строк.md`
  (снимок на ту дату: там 71 тысяча строк, сейчас 82,8 — читать как историю).
  Собирается ли он, пока неизвестно: локально Flutter SDK нет, проверяет CI.
- **Точка входа**: `backend/src/main.py`
- **API**: префикс `settings.API_V1_STR` (см. `backend/src/config.py`), роутер `backend/src/api/api_v1/api.py`
- **Локальный Python бэка**: 3.11 (`backend/.python-version`) — pydantic 1.10 несовместим с 3.12.

## Правила разработки в этом репозитории
- **Клиент-серверная граница**: фронт и бэк общаются только по REST через `/api/v1`.
  Никаких импортов между `backend/` и `frontend/`, никакой общей бизнес-логики.
  Общим может быть только клиент, **сгенерированный** из OpenAPI.
- **Не ломать работающее**: бэкенд в проде. Меняя контракт API, оставляй старый путь
  живым и помеченным `deprecated`, а не удаляй.
- **Не коммить секреты**: `.env`, `.test.env` и любые пароли/ключи не добавлять в git.
- **Правя фронт — сначала макет, потом код.** Кадр из Figma смотреть до правки:
  код подрядчика местами расходится с макетом, и повторять его нельзя. Где
  подгонка недорогая — переписывать Flutter под макет попутно; где тянет за
  собой чужой экран целиком — фиксировать расхождение словами. Порядок
  источников и как достать кадр:
  `els-vault/knowledge/decisions/фронт правится по макету, а не по коду подрядчика.md`.
- **Соблюдать стиль**: формат и линт через Ruff (см. `backend/pyproject.toml`).
- **Миграции**: изменения моделей сопровождаются Alembic миграциями.
- **Проверка изменений**: после правок запускать `make lint` и `make test` из корня репо.
- **Команды**: всё через корневой `Makefile` (`make help` покажет список).
  `make up` — весь стек в docker, `make dev` — только бэкенд локально.

## Obsidian Knowledge Vault
**Хранилище знаний (внутри репозитория)**: `els-vault/`

### При старте сессии
1. Прочитай `els-vault/00-home/index.md` — карта всего живого.
2. Прочитай `els-vault/00-home/текущие приоритеты.md` — там **только
   открытое**; закрытые работы оттуда убраны намеренно.
3. Если задача касается конкретного модуля/сущности — найди и прочитай
   заметку в `els-vault/knowledge/` или `els-vault/atlas/`.

**В `els-vault/archive/` по умолчанию не ходи.** Там планы закрытых работ,
старая хроника и снимки состояния на прошедшие даты. Заметки оттуда не
перечислены в `index.md`, они описывают то, чего уже нет, и в контексте
только мешают. Открывать — по прямой надобности: понять, почему когда-то
решили так. См. `els-vault/archive/README.md`.

### Правило совместимости (Windows-safe)
- В `els-vault/` нельзя использовать символы `< > : " / \ | ? *` в именах файлов.
- Нельзя заканчивать имя файла пробелом или точкой.
- Для проверки: `make vault-check`.

### При завершении (пользователь пишет: «сохрани сессию»)
1. Создай заметку в `els-vault/sessions/` с датой и кратким логом работы.
2. Обнови `els-vault/00-home/текущие приоритеты.md`. Файл держим коротким:
   **закрытое из него убираем**, а не сдвигаем вниз. Если закрытого набралось
   много — переноси в `els-vault/archive/состояние/`. Разрослось за 250 строк
   — время резать снова.
3. Если принято решение — создай/обнови заметку в `els-vault/knowledge/decisions/`.
4. Если найден/починен баг — создай/обнови заметку в `els-vault/knowledge/debugging/`.
5. Обнови `els-vault/00-home/index.md`, если появились новые важные заметки.
