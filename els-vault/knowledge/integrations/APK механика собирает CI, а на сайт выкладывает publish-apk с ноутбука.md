# APK механика собирает CI, а на сайт выкладывает publish-apk с ноутбука

Механик ставит приложение не из магазина, а со страницы
`https://els23.ru/app` под своим логином. Цепочка от коммита до телефона:

1. **CI `frontend.yml`** на push в `main` собирает релизный APK ключом из
   секретов (`SENTRY_DSN` тоже оттуда) и кладёт артефакт `els-apk`; в логе
   печатает sha256. По кнопке (`workflow_dispatch`) можно собрать с любой
   ветки — тогда выкладывать через `--run <id>`.
2. **`make apk-publish`** (`scripts/publish-apk.sh`) — с ноутбука, не с
   сервера: у сервера нет `gh`. Скрипт качает артефакт, берёт версию из
   `pubspec.yaml` того же коммита тем же awk, что CI, сверяет sha256 с
   логом, отказывается от сборки на debug-ключе и копирует в том
   `static_data` бэкенда: сначала APK, потом `release.json` — бэк считает
   «манифест есть, файла нет» за «раздавать нечего», окна с 404 не бывает.
3. **Бэкенд** `/api/v1/app/release` (версия, размер, «что нового»),
   `/app/link` → ссылка на минуту, `/app/download` через `X-Accel-Redirect`
   nginx. Без токена — 401: APK не публичный.
4. **Приложение** при старте сравнивает свой `versionCode` с `release.json`
   и показывает плашку «Вышла версия X · Обновить» → экран «Приложение».

`version.json` из старых формулировок плана — это и есть `release.json`,
отдельного файла нет.

## Что важно не забыть

- Локальный `flutter build apk` подписан debug-ключом — механикам только
  из CI. Ключ релиза живёт в секретах.
- `GET /app/download` не отдаёт `Range`: докачки после обрыва нет.
- В томе копятся старые `els-1.0.x.apk` — бэк их не читает, чистить руками.
- Бэкенд от выкладки APK не зависит: правка только фронта → `apk-publish`
  без `make prod-deploy`; правка сайта — деплой нужен, веб собирает
  `release`.
- Порядок релиза целиком — `docs/server-deploy.md` §3.
