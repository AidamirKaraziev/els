# Правка примонтированного файла не доезжает до контейнера

## Симптом

После правки `nginx.conf` сайт продолжал работать по-старому, а проверка
конфига внутри контейнера отвечала странным:

```
nginx: [emerg] open() "/etc/nginx/conf.d/default.conf" failed
(2: No such file or directory)
```

Файл при этом на месте, и nginx с ним же работает. То есть контейнер
одновременно и обслуживает запросы, и не находит свой конфиг.

## Настоящая причина

Монтирование **отдельного файла**, а не каталога:

```yaml
- ./infra/nginx.conf:/etc/nginx/conf.d/default.conf:ro
```

docker привязывается к конкретному inode. И `git pull`, и почти любой
редактор не дописывают файл на месте, а создают новый и переименовывают —
inode меняется. Монтирование остаётся указывать на старый, уже отвязанный
inode: контейнер видит либо прежнее содержимое, либо ничего.

Перезапуск контейнера не помогает — монтирование создаётся заново только при
пересоздании.

## Как починили

Общая часть конфига переехала в каталог `infra/nginx/`, который монтируется
целиком: `- ./infra/nginx:/etc/nginx/els:ro`. Каталог отслеживается по пути,
а не по inode, поэтому правки внутри применяются обычным `nginx -s reload`.

Файл, задающий режим (`http.conf` или `https.conf`), по-прежнему монтируется
поштучно — но он меняется только при переключении HTTP/HTTPS, а это всё
равно требует пересоздания. Для этого есть `make prod-nginx`, который
пересоздаёт контейнер и сразу прогоняет `nginx -t`.

## Урок

Поймано локально, до выката. Если бы не поймали, выстрелило бы ровно в
момент включения HTTPS: конфиг подменён, контейнер перезапущен, а сайт
остался на HTTP без единого сообщения об ошибке.

Правило простое: **bind-mount одного файла живёт до первой его перезаписи**.
Если файл предполагается редактировать — монтируйте каталог. Если всё же
файл, то в инструкции должно стоять «пересоздать контейнер», а не
«перезапустить», и написанное надо проверять, а не додумывать: инструкция с
`restart` была написана здесь же и оказалась неверной.
