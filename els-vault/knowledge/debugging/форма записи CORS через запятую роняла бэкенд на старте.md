# Форма записи CORS через запятую роняла бэкенд на старте

## Симптом

Прод лёг ровно в момент включения HTTPS, при выполнении миграций:

```
pydantic.env_settings.SettingsError:
error parsing env var "BACKEND_CORS_ORIGINS"
```

В `.env` было записано по документации:
`BACKEND_CORS_ORIGINS=https://els23.ru,https://www.els23.ru`

Показательно, что сайт при этом открывался: nginx отдавал фронт, а API
отвечал 502. Со стороны выглядело как «HTTPS сломал всё», хотя переключение
как раз прошло правильно.

## Настоящая причина

pydantic 1.x разбирает значения полей сложных типов (`List`, `Dict`) **как
JSON ещё до валидаторов**. В `config.py` есть валидатор
`assemble_cors_origins` с `pre=True`, который умеет резать строку по
запятым, — но до него дело не доходит, всё падает раньше, в
`EnvSettingsSource.__call__`.

То есть форма через запятую не работала **никогда**. Она была написана в
README, в комментарии `main.py` и в инструкции по деплою — просто до этого
дня переменную никто не заполнял, а с пустым значением всё работало.

## Как починили

В `Settings.Config` добавлен `parse_env_var`, принимающий обе формы: и JSON
`["https://a"]`, и человеческую `https://a,https://b`. По исходникам pydantic
проверено, что метод вызывается только для сложных типов — обычные строки
вроде `DB_USER` он не трогает.

Тесты в `tests/test_config_cors.py` проверяют семь форм записи. Что тест
ловит именно эту поломку, проверено снятием правки: падает четыре случая из
семи, ровно на формах через запятую.

Быстрый выход из аварии, пока собирается новый образ, — записать значение
JSON-массивом: эта форма работала и со старым кодом.

## Урок

Расхождение между документацией и поведением опаснее обычной ошибки: оно
срабатывает в тот момент, когда человек впервые делает то, что написано в
инструкции, — то есть при выкате в прод.

Если в коде есть валидатор, обрабатывающий какой-то формат, это ещё не
значит, что формат работает. Между переменной окружения и валидатором может
стоять чужой слой разбора.
