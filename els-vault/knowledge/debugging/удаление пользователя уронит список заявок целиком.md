# Удаление пользователя уронит список заявок целиком

Не починено. Найдено попутно, при написании тестов на фильтры заявок.

## Симптом

Заявка без автора роняет **всю выдачу** `/order/all` с 500 — не только свою
строку. Список задач просто перестаёт открываться, для всех сразу.

Вылезло на тестовой фикстуре, которая создавала заявки без `creator_id`:

```
pydantic.error_wrappers.ValidationError: 1 validation error for OrderGet
creator_id
  none is not an allowed value (type=type_error.none.not_allowed)
```

## Настоящая причина

Две вещи, противоречащие друг другу.

В схеме ответа `OrderGet` поле объявлено обязательным:

```python
creator_id: UniversalUserGet
```

А в модели внешний ключ разрешает обнуление:

```python
creator_id = Column(Integer, ForeignKey(UniversalUser.id, ondelete="SET NULL"))
```

То есть база **сама** обнулит автора при удалении пользователя — это её
штатное поведение, прописанное в схеме таблицы. После этого сериализация
ответа падает, а падает она на всём списке, потому что собирается целиком.

Сейчас этого не случалось только потому, что пользователей не удаляли.

## Как чинить

`creator_id: Optional[UniversalUserGet]` в схеме. Снимок контракта это не
заденет — он отслеживает обязательные параметры и тело запроса, а не поля
ответа. Но типизация ответа меняется, поэтому решение за заказчиком.

Стоит заодно посмотреть остальные поля `OrderGet` и других схем на то же
расхождение: `executor_id`, `object_id`, `fault_category_id` и
`reason_fault_id` объявлены `Optional`, а `creator_id` — единственный, кто
выбивается.

## Урок

Каждое поле схемы ответа, за которым стоит внешний ключ с `ondelete="SET
NULL"`, обязано быть `Optional`. Иначе удаление строки в справочнике роняет
не одну запись, а весь список, где она встречается.

Проверять это надо не глазами по коду, а по списку внешних ключей: в этом
проекте `SET NULL` стоит почти везде.
