# Аудит авторизации на 2026-08-12 - семь дыр в бэкенде

Найдено при разборе перед [[план - рефакторинг авторизации и ролей]].
Ничего из этого пока не починено.

## 1. Вход в систему паролем «1»

Пользователь `id=1`: email `1`, пароль `1`, роль «Админ», активен. Проверено
локально на дампе с прода — `passlib` подтверждает совпадение хеша.

Одного удаления строки в базе мало: `create_super_admin()` в
`src/core/db/init_db.py` вызывается на каждом старте приложения и создаёт
аккаунт заново, если пользователя с `id=1` нет. Пароль зашит в код:

```python
hashed_password = get_password_hash("1")
user_in = UniversalUserCreate(id=1, name="Супер Админ", email="1", ...)
```

При этом в `config.py` уже есть `FIRST_SUPERUSER` и `FIRST_SUPERUSER_PASSWORD`,
но сидер их не читает.

## 2. Уволенный сотрудник ходит по системе ещё восемь дней

`deps.get_current_universal_user_by_bearer` проверяет только подпись токена и
существование пользователя. Флаг `is_actual` не смотрит **никто**, кроме
самого входа.

То есть архивирование сотрудника (`/cp/admin/archiving-users/`) не отбирает
доступ. Токен живёт `ACCESS_TOKEN_EXPIRE_MINUTES = 60*24*8` — восемь суток, и
отозвать его нечем.

## 3. Проверок роли на эндпоинтах нет ни одной

160 живых ручек. 133 из них висят на `get_current_universal_user_by_bearer` —
это аутентификация, но не авторизация: он одинаково пропускает админа,
механика и клиента.

Проверки роли есть, но лежат внутри CRUD-слоя магическими числами — 37 мест
вида `if user.role_id != 1`, возвращающих коды `-1`, `-2`, `-5`, которые потом
разбирает `templates_raise.get_raise`. Куда эти проверки не дотянулись, там
доступ открыт всем.

## 5. Файлы отдаются кому угодно, и путь склеивается вручную

`src/api/api_v1/endpoints/admin.py`, ручка `/static/{filename:path}`:

```python
async def get_site(filename):
    filename = "static/" + filename
```

Ни токена, ни нормализации пути. Через эту ручку отдаются фото заявок,
дефектные акты, удостоверения личности сотрудников и PDF-отчёты. Конкатенация
с `{filename:path}` — заготовка под выход за пределы каталога, это надо
проверить отдельно на запущенном приложении.

## 6. SECRET_KEY по умолчанию случайный

```python
SECRET_KEY: str = secrets.token_urlsafe(32)
```

Если переменной нет в `.env`, ключ новый на каждый рестарт процесса. Все
токены протухают молча, без единой записи в логе, а выглядит это как «опять
разлогинило». В нескольких воркерах uvicorn ключи будут ещё и разные у каждого.

## 7. Уникальности email нет, вход чувствителен к регистру

```python
__table_args__ = (UniqueConstraint("email", "is_actual", name="_email_is_actual_uc"),)
```

Составное ограничение с `is_actual` уникальности email не даёт: `NULL` в
булевом поле обходит его целиком, а два пользователя с одним адресом и разным
`is_actual` — легальны. При этом `entrance_universal_user` ищет по email без
фильтров и берёт `.first()`, то есть при коллизии пустит не в тот аккаунт.

Отдельно: поиск идёт по точному совпадению строки. В базе есть
`Голдобин@mail.ru`, `Закора@mai.ru`, `Zarja@rambler.ru` — человек, набравший
адрес строчными, не войдёт.

## Мелочь, но чинить в тот же заход

`create_token` в `src/core/security.py`:

```python
claim_extra_fields: List[str] = getattr(settings, "TOKEN_CLAIMS_EXTRA_FIELDS", [])
...
claim_extra_fields.append(field)
```

`getattr` возвращает **сам список из настроек**, а не копию. Каждый вызов
дописывает в него элементы — список растёт всё время жизни процесса.

Там же лежат две функции-близнеца, `create_token` и
`create_token_universal_user`, побайтово одинаковые.

Ещё в `deps.py` две мёртвые функции, выглядящие как рабочие:
`get_current_universal_user` объявлен с `token: str = Depends()` — пустым
`Depends`, а `get_current_active_universal_user` зовёт
`crud_universal_users.is_active`, которого в классе нет.

## Что из этого состояние базы, а что кода

База чистая: 20 пользователей, дублей email нет, все пароли bcrypt, `role_id`
заполнен у всех. Так что миграции на уникальный индекс и переименования
пройдут без ручной чистки. Проблемы — в коде, а не в данных.
