# Ссылки на файлы вели на порт 8000, которого снаружи нет

## Симптом

В браузере на каждой аватарке:

```
http://213.171.3.254:8000/api/v1/static/universal_user/1/photo/…
net::ERR_EMPTY_RESPONSE
```

## Настоящая причина

Три независимые поломки, сложившиеся в одну.

**Порт брался из настроек, а не из запроса.** Тринадцать геттеров собирали
адрес одинаково: `request.url.hostname + ":" + str(settings.APP_PORT)`.
`hostname` — это только имя хоста, без порта, а `APP_PORT` всегда `8000`.
Браузер же ходит через nginx на 80 или 8080, и порт 8000 наружу не
публикуется — в compose стоит только `expose`.

**Раздачи статики не было вообще.** `StaticFiles` в `backend/src` не
использовался нигде, роута `/api/v1/static/` не существовало. Файлы
исправно писались в `/app/static/`, но отдавать их было некому. То есть
фотографии не открывались ни разу за всё время жизни проекта.

**nginx терял порт при проксировании.** `proxy_set_header Host $host` — у
этой переменной порт отрезан. Даже с исправленным кодом бэкенд получил бы
`els23.ru` без порта и построил бы ссылку на 80-й.

## Как починили

Сборка адреса вынесена в `src/getters/static_url.py`, тринадцать копий
заменены вызовом. Вместо `hostname` + настроечный порт теперь
`request.url.netloc` — это заголовок `Host` целиком, ровно тот адрес, по
которому пришёл клиент. Ссылка сама подстраивается под localhost, IP и домен.

Раздачу отдали nginx, а не uvicorn: том `static_data` примонтирован во
фронт-контейнер только на чтение. На сервере с одним ядром это принципиально
— каждая картинка через приложение занимала бы единственный рабочий процесс,
и лента с аватарками подвешивала бы API целиком.

В nginx `Host` передаётся как `$http_host`.

Схему (`http://`) бэкенд по-прежнему не добавляет: фронт дописывает её сам
в 111 местах. Это отдельная история, см. `ApiConfig.scheme`.

## Урок

Проверять «вроде бы работающие» ссылки не по коду, а запросом. Здесь код
выглядел правдоподобно во всех трёх местах по отдельности.

И характерный признак: если приложение строит абсолютный URL из настроек, а
не из входящего запроса, оно почти наверняка сломается при первом же
изменении топологии — за прокси, на другом порту, под другим доменом.
