# Бэкенд в контейнере падал на DB_HOST из локального .env

После первого `make up` веб-приложение отдавалось, а любой запрос к API
возвращал `502 Bad Gateway`. В логах бэкенда:

```
sqlalchemy.exc.OperationalError: connection to server at "localhost" (::1),
port 5435 failed: Connection refused
```

Симптом выглядел как «postgres не поднялся», но контейнер postgres был
`healthy`. Настоящая причина в другом: в корневом `.env` лежат настройки для
запуска **с хоста** — `DB_HOST=localhost`, `DB_PORT=5435`. Compose передавал их
в контейнер через `env_file`, и бэкенд честно стучался в `localhost`, то есть
сам в себя.

## Как починили

Топологию сети задаёт compose, а не `.env`:

```yaml
    environment:
      DB_HOST: postgres
      DB_PORT: 5432
      DB_USER: ${DB_USER}
```

Блок `environment` в compose приоритетнее `env_file`, поэтому локальные
значения больше не мешают контейнеру, а контейнерные — локальному запуску.
Хардкод здесь уместен: внутри этой compose-сети база всегда `postgres:5432`.

## Урок

Один `.env` на две среды работает только для того, что в обеих средах
одинаково: логин, пароль, имя базы. **Адрес и порт зависят от того, кто
спрашивает**, поэтому их место в compose, а не в общем файле.

Проверять после правки compose стоит не «контейнеры поднялись», а живой запрос
через прокси: `curl` к `/api/v1/locations/` показал бы 502 сразу.

Заодно там же вылезло, что `POSTGRES_PASSWORD` подставлялся пустым: приложение
читает `DB_PASS`, а шаблоны в `backend/envs/` называют переменную
`DB_PASSWORD`. Сделано `${DB_PASSWORD:-${DB_PASS}}` — работает с любым именем.
