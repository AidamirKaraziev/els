# Балл считается в Python, а запрос отдаёт строки

Три виджета главной считают агрегаты в SQL: запрос возвращает готовые
`count`, `avg` и проценты. Топ сотрудников устроен наоборот — запросы отдают
строки как есть, а арифметика живёт чистыми функциями в
`src/services/employee_score.py`.

```python
# crud: строки, а не агрегаты
.with_entities(
    Order.executor_id.label("executor_id"),
    Order.created_at.label("created_at"),
    func.coalesce(Order.accepted_at, Order.in_progress_at).label("reacted_at"),
    FaultCategory.code.label("category_code"),
    (Object.mechanic_id == Order.executor_id).label("is_own_object"),
)

# service: ни одного обращения к базе
def score_employees(*, employees, orders, maintenance, ...) -> List[EmployeeScore]:
```

Тест формулы обходится без Postgres целиком:

```python
scores = score_employees(
    employees=[employee(1)],
    orders=[order(executor_id=1, reaction=datetime.timedelta(minutes=45))],
    ...
)
assert scores[1].metrics["reaction"] == 75.0
```

## Почему так

- Норматив реакции зависит от тяжести категории, вес работы — от категории и
  длины чек-листа, вес непосчитанной метрики перераспределяется между
  остальными. Выразить это `CASE`-ами значило бы записать договорённость с
  заказчиком на языке, на котором её нельзя прочитать вслух.
- Балл — предмет разговора с людьми, и его будут менять. Правка веса не
  должна означать правку запроса.
- Тридцать девять тестов формулы идут за 0,02 секунды и не требуют базы.
  Проверять на них мутации дёшево — а без мутаций зелёный прогон ничего не
  значит, см. [[статистика - агрегаты за период через FILTER и общий подзапрос]].

## Что важно не забыть

- **Так можно, пока строк мало.** Здесь это заявки и ТО одного месяца в
  границах области видимости — десятки, в худшем случае сотни. Для выборки в
  сотни тысяч строк приём не годится, и переезжать пришлось бы в SQL.
- **Область видимости всё равно применяется в запросе**, а не при подсчёте.
  Отфильтровать после выборки значило бы сначала достать чужое.
- Строки запроса и поля, которые читает функция, связаны только именами
  меток. Убрал поле из `with_entities` — падение будет в скоринге и не сразу
  очевидное; поэтому лишние метки в запросах не держим.
- Мутационная проверка нужна обеим половинам: отдельно формуле, отдельно
  запросам. Ошибка «в выборку попали незакрытые заявки» тестами формулы не
  ловится вовсе.

Приём подойдёт любому расчёту, где правило важнее объёма данных: премии,
рейтинги, скоринги, любые пороги, о которых договариваются с заказчиком.
