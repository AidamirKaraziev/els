# Правило экрана живёт чистой функцией рядом с данными

Какая кнопка положена в каком состоянии — это правило, а не вёрстка. Оно
вынесено из экрана в `frontend/lib/mechanic/data/tasks.dart`:

```dart
ActControls actControls(MaintenanceState state, {required bool allDone}) {
  switch (state) {
    case MaintenanceState.inWork:
      return ActControls(
        main: allDone ? ActAction.close : ActAction.open,
        canPause: true,
        canReportProblem: true,
      );
    // ...
  }
}
```

Экран получает набор и только рисует его; подпись главной кнопки даёт
`controls.mainLabel`. Проверяется правило юнит-тестом на пять состояний —
`frontend/test/mechanic/act_controls_test.dart`.

## Почему так

Карточку ТО виджет-тестом не поднять: она грузит акт через
`MechanicWorkspace.current`, а рабочее место создаётся приватным
конструктором и лезет в `PreferencesStore`. Заводить ради теста ещё один
параметр-щель в экран — платить вёрсткой за проверку правила. Чистая функция
проверяется без Flutter вообще и читается как текст: «приостановленное
возобновляется, второй раз не приостановить».

Тот же приём рядом: `maintenanceState` разбирает строку списка в состояние
работы, и её читают **и** список, и карточка. Два разбора одних и тех же
полей рано или поздно разъезжаются, и тогда список говорит одно, а карточка
другое.

## Что важно не забыть

- Занятость экрана в правило не тащить. `canPause` отвечает на вопрос
  «положена ли пауза в этом состоянии», а `_busy` — «идёт ли отправка прямо
  сейчас». Смешаешь — кнопка будет исчезать на каждое нажатие вместо того,
  чтобы гаснуть, и строка под кнопкой запрыгает.
- Правило должно лежать рядом с данными, а не рядом с экраном: его читают
  оба экрана и тесты, а `screens/` тянет за собой `material.dart`.

Применимо там же, где следующая работа: раздел «Сейчас в работе» у прораба
будет решать по тем же состояниям, и правило для него стоит писать так же.
