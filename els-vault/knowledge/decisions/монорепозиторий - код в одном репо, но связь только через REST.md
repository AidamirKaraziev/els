# Монорепозиторий - код в одном репо, но связь только через REST

## Решение

Бэкенд и фронтенд живут в **одном git-репозитории**, но остаются **двумя
независимыми приложениями**. Единственный канал связи — HTTP REST на `/api/v1`.

## Почему

- Один репозиторий = одна история, один CI, один `docker compose up`, одна точка
  правды по контракту API. Заказчику видно движение по всему проекту сразу.
- Клиент-серверная граница сохраняется, потому что фронт может понадобиться
  собирать/деплоить отдельно, а бэк — обслуживать ещё и мобильное приложение
  (в тегах эндпоинтов уже есть «Мобильное приложение / …»).

## Границы, которые нельзя нарушать

- Фронт **не импортирует** Python-код бэка, бэк **не рендерит** фронтовые шаблоны.
- Никаких «общих» модулей с бизнес-логикой между частями. Общим может быть только
  **сгенерированный из OpenAPI** клиент/типы — артефакт сборки, не рукописный код.
- У каждой части свой менеджер зависимостей, свой линт, свои тесты, свой Dockerfile.
- Бэкенд не знает про существование конкретного фронта: сломать контракт нельзя
  даже «по-быстрому», потому что на нём же висит мобильное приложение.

## Как разложено на самом деле (сделано 2026-08-11)

```
backend/   src, alembic, tests, pyproject, Dockerfile, static, envs, scripts
frontend/  появится вместе с кодом фронта
infra/     docker-compose.yml, docker-compose.test.yml
els-vault/ база знаний
docs/, readme_file/, scripts/ (инструменты репо)
```

Детали, о которые легко споткнуться:

- Все команды — из корня через `Makefile`. `make up` теперь поднимает **весь стек
  в docker**, а локальный бэкенд с автоперезагрузкой — это `make dev`
  (раньше `make up` запускал именно uvicorn).
- Пути внутри `infra/docker-compose.yml` относительны **корня репо**, поэтому
  вызывать его нужно с `--project-directory .` — иначе не найдётся ни контекст
  сборки, ни `.env`. В Makefile флаг уже зашит.
- `.env` и `.test.env` остались **в корне**, чтобы не переделывать окружение на
  сервере. `backend/src/config.py` и `tests/conftest.py` ищут их по абсолютному
  пути в двух местах (корень и `backend/`), так что рабочий каталог не важен.
- Локальный Python бэкенда закреплён файлом `backend/.python-version`:
  [[pydantic 1.10 ломается на Python 3.12 - venv бэкенда закреплён на 3.11]].

## Следствия

- В CI две независимые джобы: backend (ruff + pytest) и frontend (линт + сборка).
- Контракт фиксируется снапшотом `openapi.json` в репозитории, изменение снапшота
  без осознанного обновления = упавший тест.
- Перенос файлов делаем **с сохранением git-истории**, а не копированием.
