# Тяжесть категории - порядок берётся из id, отдельного ранга нет

## Решение

В топе поломок объекты сортируются по числу заявок, а при равном счётчике
выше встаёт тот, у кого случилось более тяжёлое событие. «Более тяжёлое» —
это **меньший `fault_category.id`**: классификация засеяна по убыванию
тяжести, id 1 это AA (застревание пассажира), дальше А, В, Н.

В запросе это `min(coalesce(fault_category.id, 1000000))` как второй ключ
сортировки. Заявка без категории получает заведомо больший ранг и тай-брейк
проигрывает.

Отдельную колонку `severity_rank` заводить не стали.

## Почему

- Заказчик выбрал сортировку «по числу заявок, при равенстве тяжёлые выше»
  именно потому, что цифра в строке должна совпадать с порядком: никто не
  спросит, почему лифт с четырьмя поломками стоит выше лифта с шестью.
  Взвешенный индекс проблемности (AA=5, А=3, В=2, Н=1) рассматривали и
  отклонили — веса пришлось бы защищать перед заказчиком, а порядок перестал
  бы читаться по счётчику.
- Порядок id — не случайность, а сама отраслевая классификация. Она стабильна
  и записана в `create_initial_data`.
- Категория, заведённая админом позже, получает больший id и считается
  наименее тяжёлой. Это безопасное умолчание: новая непонятная категория не
  выталкивает объект наверх.

## Цена решения

Неявная связь между порядком id и смыслом. Если кто-то пересоздаст справочник
в другом порядке или вставит новую категорию с ручным маленьким id, тай-брейк
поедет — без ошибки, просто другим порядком строк. Допущение записано в
докстринге `src/crud/crud_statistics.py`, чтобы его нашли до того, как оно
удивит.

## Когда вернёмся

Как только тяжесть понадобится где-то ещё, кроме тай-брейка, — например для
взвешенного индекса, для цветовой шкалы или для SLA по категориям — заводим
явную колонку ранга и переносим смысл туда.
