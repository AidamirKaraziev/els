# Справочник поломок - флаг counts_as_breakdown вместо списка id в коде

## Решение

Признак «считать ли заявки этой категории поломкой» живёт колонкой
`fault_category.counts_as_breakdown`, а не списком id в запросе. Рядом
добавлена колонка `code` с коротким кодом категории (AA, А, ТО, КР).
Миграция `a1c7f3d92b40`.

Категории неисправностей в этом проекте — не «типы поломок», а отраслевая
классификация по тяжести:

| id | код | считать поломкой |
|---|---|---|
| 1 | AA | да, застревание пассажира |
| 2 | А | да, остановка лифта |
| 3 | В | да, ухудшение характеристик |
| 4 | Н | да, незначительные проблемы |
| 5 | Д | да, заказчик или другие |
| 6 | ТО | нет, плановые работы |
| 7 | ПТО | нет, освидетельствование |
| 8 | КР | нет, капитальный ремонт |
| 9 | С | да, проблемы по связи |
| 10 | Л | нет, ложный вызов |

Заявка **без категории считается поломкой**: пустое поле означает
недозаполненную заявку, а не плановую работу, и терять реальный выезд нельзя.

## Почему

- Список `(6, 7, 8, 10)` в SQL сломался бы молча. Админ заводит категорию
  через админку, она не попадает в список, и статистика начинает врать —
  без ошибки, без падения, просто другими цифрами.
- Новая категория получает `counts_as_breakdown = true` по умолчанию. Лучше
  показать лишнюю поломку и услышать вопрос, чем тихо потерять выезд.
- `code` нужен интерфейсу: полное имя «AA (Застревание пассажира. Опасность)»
  в чип свода не помещается. Вытаскивать код из имени регуляркой — способ
  однажды получить пустую строку после правки названия через админку.

## Цена решения

Две колонки, которые надо не забыть проставить у новой категории. В
`FaultCategoryCreate` и `FaultCategoryUpdate` они необязательные, так что
админ может завести категорию и не задумываться — но тогда она попадёт в
статистику поломок.

## Когда вернёмся

Если появится третье состояние помимо «поломка / не поломка» — например,
«гарантийный случай» или «работы по договору» — флага перестанет хватать и
нужен будет справочник типов, а не булев признак.
