# План работ - интеграция фронта и рефакторинг

Живой документ. Обновляется по мере закрытия этапов и после аудита фронта.

## Принцип

Сначала **страховочная сетка**, потом правки. Каждый этап заканчивается зелёными
тестами и рабочим `docker compose up`. Ничего из работающего не ломаем: старые
пути API остаются живыми и помечаются `deprecated`, пока фронт не переедет.

### Как заливать код фронта, когда доступ появится
Нужна **история**, а не копия файлов, поэтому не «скачать ZIP и положить рядом»:

```
git remote add frontend https://github.com/<владелец>/<репо>.git
git fetch frontend
git subtree add --prefix=frontend frontend <ветка>
```

`subtree add` кладёт чужой репозиторий в подкаталог вместе со всеми его коммитами.
Если Вова не даёт доступ — годится `git bundle` или архив, но тогда история
схлопнется в один коммит и авторство размажется.

### Этап 2 — страховочная сетка (24–40 ч, начат 2026-08-11)

**Сделано**: снимок контракта API (`backend/tests/snapshots/openapi_surface.json`,
157 ручек) и тест `test_openapi_contract.py`. В снимок входят пути, методы,
обязательные параметры и обязательные поля тела — но не названия и описания,
иначе тест падал бы на каждой правке текста и его начали бы обновлять не глядя.
Обновление осознанное: `make openapi-update`, дифф снимка показывать в ревью.
Проверено намеренной поломкой: тест ловит пропавшую ручку, новую ручку и
изменение обязательных полей, сообщение читаемое.

Там же `test_deletion_is_not_done_via_get` — держит планку по удалению через GET.
Их ровно 4 (`locations`, `steps`, `sub-steps`, `working-specialty`), список зашит
в тест: новую такую ручку добавить не выйдет, а починенную придётся из списка
убрать, поэтому цифра всегда честная.

**Осталось**: интеграционные тесты на критические потоки — авторизация и роли,
объекты, наряды, акты, дефектные акты, генерация PDF. Фабрики данных вместо
ручных фикстур. Отчёт по покрытию как базовая цифра.

### Этап 6 — доработка фронта (переоценено после аудита)
Прежний ориентир 80–160 ч снят. Два пути:

| Путь | Часы | Что получаем |
|------|------|--------------|
| Довести как есть до сдачи | 60–100 | заказчик доволен, каждая следующая правка стоит втрое |
| Привести в порядок, потом дописывать | 190–290 | единый API-клиент, один набор экранов вместо трёх-четырёх |

Рабочий вариант — гибрид: сначала ~40 ч на минимум (адрес бэкенда в конфиг,
убрать заглушку `reqres.in`, поднять сборку) — это видимый результат для
заказчика; дедупликацию ролей делать потом поэкранно, за счёт бюджета на
новые разделы.

Порядок внутри этапа:
1. Дождаться первого прогона CI — узнать, собирается ли код под Dart 3.
2. Один конфиг адреса API вместо двух зашитых IP, перевести на HTTPS.
3. Единый клиент на dio + слой репозиториев; переносить экраны по одному.
4. Свести `screns/` и `foreman/` в один набор с ролевым поведением.
