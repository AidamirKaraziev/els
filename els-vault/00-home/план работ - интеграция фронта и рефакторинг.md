# План работ - интеграция фронта и рефакторинг

Живой документ. Обновляется по мере закрытия этапов и после аудита фронта.

## Принцип

Сначала **страховочная сетка**, потом правки. Каждый этап заканчивается зелёными
тестами и рабочим `docker compose up`. Ничего из работающего не ломаем: старые
пути API остаются живыми и помечаются `deprecated`, пока фронт не переедет.

## Этапы

### Этап 0 — чистая точка отсчёта — ГОТОВО 2026-08-11
Тесты локаций расконсервированы, `db_session` снова откатывает транзакцию,
добавлен тест на саму изоляцию фикстуры, тестовая БД поднимается контейнером,
`make lint` зелёный. 9 тестов проходят.

### Этап 1 — каркас монорепозитория — ГОТОВО 2026-08-11
Раскладка `backend/` + `infra/` сделана через `git mv` (история файлов цела),
корневой `Makefile` стал единой точкой входа, CI на GitHub Actions поднят

Осталось до полного закрытия этапа: каталог `frontend/`, сервис фронта в compose,
nginx как единая точка входа, джоба фронта в CI — всё это появится вместе с кодом.
Детали раскладки: [[монорепозиторий - код в одном репо, но связь только через REST]].

### Как заливать код фронта, когда доступ появится
Нужна **история**, а не копия файлов, поэтому не «скачать ZIP и положить рядом»:

```
git remote add frontend https://github.com/<владелец>/<репо>.git
git fetch frontend
git subtree add --prefix=frontend frontend <ветка>
```

`subtree add` кладёт чужой репозиторий в подкаталог вместе со всеми его коммитами.
Если Вова не даёт доступ — годится `git bundle` или архив, но тогда история
схлопнется в один коммит и авторство размажется.

### Этап 2 — страховочная сетка (24–40 ч)
Снапшот `openapi.json` в репозитории + тест на его дифф — контракт перестаёт
меняться молча. Интеграционные тесты на критические потоки: авторизация и роли,
объекты, наряды, акты, дефектные акты, генерация PDF. Фабрики данных вместо
ручных фикстур. Отчёт по покрытию как базовая цифра.

### Этап 3 — схема БД в порядок (16–24 ч)
`alembic revision --autogenerate` на пустой базе, разбор дифа между 33 моделями и
3 миграциями, добивка недостающего. Проверка на копии боевой базы, а не на проде.

### Этап 4 — безопасность и REST-гигиена (24–40 ч)
Вернуть авторизацию на 25 открытых ручек, вынести проверку ролей в одну зависимость
вместо копипасты. Удаление перевести на `DELETE` (старые GET-ручки живут помеченные
`deprecated`). CORS по списку доменов. `SECRET_KEY` обязательным из окружения.
Единый обработчик ошибок вместо магических числовых кодов.

### Этап 5 — аудит кода Вовы (8–16 ч, фиксированная цена)
Инвентаризация: стек, сборка, какие экраны есть и какие живы, насколько фронт
соответствует реальному API, что переиспользуется, что переписывается.
**Результат — письменный отчёт и оценка этапа 6.** Оценивать фронт до аудита нельзя.

### Этап 6 — доработка фронта
Оценка появляется после этапа 5. Очень грубый ориентир до аудита:
современный стек и половина экранов рабочая — 80–160 ч; сырой код или чужой
устаревший стек — 200–400 ч и разговор с заказчиком о переписывании.

### Этап 7 — недостающие разделы
Список формируется отдельно. Каждый раздел оценивается сам по себе по факту.

## Итог по оценке

- Этапы 0–4 (бэк, инфраструктура, тесты) — **82–132 ч**, объём известен, можно
  брать фиксированной ценой.
- Этап 5 — **8–16 ч**, отдельная фиксированная цена.
- Этапы 6–7 — только почасово или после переоценки. Фиксировать цену на код,
  который не видел, — способ доплатить за чужую работу из своего кармана.
