# План - запустить проект локально в docker

Цель: `make up` в корне поднимает всю систему, веб открывается в браузере,
телефон (iOS/Android) работает с тем же бэкендом. Одна кодовая база на три
платформы, без дублирования.

## Что в docker может быть, а что нет

| Часть | В docker | Как запускается |
|-------|----------|-----------------|
| PostgreSQL | да | контейнер |
| Бэкенд | да | контейнер |
| Веб-приложение | да | сборка Flutter web внутри образа + nginx |
| iOS / Android | **нет** | с хоста, `flutter run` на устройство/симулятор |

Мобильные сборки в контейнер не заворачиваются: Android нужен SDK и эмулятор
с доступом к ядру, iOS собирается только на macOS с Xcode. Docker даёт им
**бэкенд**, а не сборку. Приложение при этом одно и то же — разница лишь в
адресе API.

## Единая точка входа

nginx отдаёт и приложение, и API с одного origin:

```
localhost:8080/           → веб-сборка Flutter
localhost:8080/api/v1/    → проксируется на backend:8000
localhost:8080/docs       → Swagger бэкенда
```

Почему так, а не два порта: браузеру не нужен CORS (origin один), а фронту не
нужно знать адрес бэкенда — достаточно относительного `/api/v1`. Телефон ходит
на тот же nginx по IP машины в локальной сети.

## Шаги

### Шаг 1 — узнать, компилируется ли код (4–12 ч, главная неизвестность)
Сборка запускается в контейнере (`frontend/Dockerfile`, образ
`ghcr.io/cirruslabs/flutter:stable`), поэтому SDK на машине для этого не нужен.
Код писался под Dart 2.17, собираться будет под Dart 3 — часть ошибок
гарантирована, объём заранее неизвестен. Пока этот шаг не закрыт, остальные
оценки условны.

Для мобильных сборок и hot reload Flutter локально всё равно понадобится —
ставить через `fvm`, чтобы версия была зафиксирована в репозитории.

### Шаг 2 — адрес API в конфиг — ГОТОВО 2026-08-11
`lib/helper/api_config.dart` — единственное место, знающее адрес бэкенда.
185 подстановок в 65 файлах заменены на `${ApiConfig.base}`, мёртвый
`IntTest.myIp` из файла с цветами убран.

- **веб** берёт `Uri.base.origin` — одна сборка работает и на `localhost:8080`,
  и на боевом домене, и по HTTPS, без пересборки и без CORS;
- **телефон** — `--dart-define=API_ORIGIN=http://<IP машины>:8080`
  (Android-эмулятор: `10.0.2.2`);
- переменная называется `API_ORIGIN`, а не `API_BASE_URL`: из origin выводится
  и префикс `/api/v1`, путать нечего.

Проверка: в собранном `main.dart.js` старого адреса `185.154.193.42` **ноль
вхождений** — dart2js выкинул мобильную ветку, потому что `kIsWeb` для веба
это компайл-тайм константа. Веб-сборка физически не может обратиться к
старому серверу.

Осталось из этого шага: заглушка `reqres.in` на экране сотрудников
(`employee_repository.dart`) — она не про адрес, а про то, что экран никогда
не подключали к нашему API.

### Шаг 3 — починить платформенные импорты (8–16 ч)
Без этого мобильных сборок не существует: `import 'dart:html'` и web-only
`image_picker_web` ломают компиляцию под Android/iOS. Точный объём (замерено
2026-08-11):

| Что | Сколько |
|-----|---------|
| `ImagePickerWeb.getImageInfo` | 26 вызовов в 13 файлах |
| `ImagePickerWeb.getMultiImagesAsFile` / `getImageAsBytes` / `getImageAsFile` | по 1–2 |
| `html.File` | 3 использования в 2 файлах |
| кросс-платформенный `image_picker` | уже используется в 2 местах |

Делается так же, как вышло с картой: один сервис в `lib/helper/`, который
отдаёт платформенно-нейтральный результат (имя файла + байты), внутри —
условный импорт `dart.library.html`. Экраны получают один и тот же вызов
и не знают, где они запущены. Это и есть «не дублировать код»: один экран,
ветка по платформе внутри одного сервиса.

### Шаг 4 — docker-стек (готово, проверяется шагом 1)
- `frontend/Dockerfile` — multi-stage: сборка web → nginx;
- `infra/nginx.conf` — проксирование `/api/v1/` на бэкенд, SPA-fallback;
- сервис `frontend` в `infra/docker-compose.yml`, порт `8080` наружу;
- бэкенд порт наружу больше не публикует — только через nginx.

### Шаг 5 — запуск на телефоне (2–4 ч)
```
flutter run -d <device> --dart-define=API_BASE_URL=http://192.168.1.X:8080/api/v1
```
Телефон и компьютер в одной сети. iOS-симулятор понимает `localhost`,
Android-эмулятор — `10.0.2.2`.

## Оценка

| Шаг | Часы | Статус |
|-----|------|--------|
| 1. Поднять компиляцию под Dart 3 | 4–12 | готово, вышло дешевле: ошибок в `lib/` не было вовсе, весь ремонт — зависимости |
| 2. Адрес API в конфиг | 2–4 | готово |
| 3. Платформенные импорты | 8–16 | осталось |
| 4. Docker-стек | — | готово |
| 5. Запуск на телефоне | 2–4 | ждёт шага 3 |

Шаг 3 можно проверять, не ставя Flutter локально: образ `cirruslabs/flutter`
несёт Android SDK, поэтому `flutter build apk --debug` внутри контейнера
покажет, компилируется ли код под мобильную платформу. iOS так не проверить —
нужен Xcode на macOS.

Дедупликация ролевых экранов (100–150 ч) в эту цель не входит — она про
стоимость дальнейшей разработки, а не про запуск.
