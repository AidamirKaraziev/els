# Журнал - изменения контракта API для фронта

Рабочий документ. Наполняется по ходу
[[план - рефакторинг авторизации и ролей]], по нему пойдёт **отдельная сессия
правок фронта** — контекстного окна на бэк и фронт разом не хватит.

Правило заполнения: на каждое изменение — что было, что стало, какие файлы
фронта это задевает. Без «какие файлы» запись бесполезна: следующей сессии
придётся заново искать по всему `frontend/lib`.

## Что уже известно про фронт

**Токен хранится одной строкой** в `SharedPreferences` под ключом `token` —
`lib/screns/auth/auth_log_and_pass/log_and_pass.dart:80`. Единственное место
записи во всём проекте. Пары access/refresh там нет и предусмотреть её негде,
кроме как переписать это место.

**Перехватчика ответов нет.** Обновление токена по `401` придётся добавлять с
нуля. Проверить, ходит ли фронт через общий клиент `dio` или каждый экран
собирает запрос сам — от этого зависит, одно это место или полсотни.

**Ветвление по ролям отсутствует.** В `log_and_pass.dart:189-196` оно
закомментировано, все роли попадают на один экран. Значит после появления
`403` на бэкенде клиент и механик увидят ошибки там, где раньше им молча
отдавались чужие данные. Экраны придётся прятать по роли, а не только чинить
запросы.

**Роль читается как вложенный объект** `role_id: {id, name}` —
`lib/screns/user/user_info.dart:72`, `lib/screns/task/view/task_screen.dart:561`.
Если поле переименуется или станет строкой, эти места отвалятся молча: там
обращение по ключу к `Map`, без типизации.

**Жёстко зашитые id ролей в путях**: `universal-user/sort-by-role/3/` и
`/2/` в `lib/screns/object/view/object_page.dart:149,167` — это выбор механика
и прораба при создании объекта.
