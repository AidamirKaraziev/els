# План - мобильное приложение механика и замыкание процесса

Заказчик принял предыдущий пул работ. Дальше замыкаем **два процесса
целиком**:

1. график ТО → задача механику в телефоне → исполнение по регламенту →
   результат у прораба;
2. заявка диспетчера → задача механику → исполнение → результат у прораба.

Оба разорваны в одном месте: **у механика нет рабочего инструмента**. Всё
остальное звено живое.

## Поток из кода подрядчика — как справочник

Само приложение (`frontend/els_mobile/`, 4280 строк, Dart 2.19, в git не
добавлено) выбрасываем: оно не войдёт даже в систему — стучится в снесённую
`/cp/sign-in/`. Но описанный в нём поток верен и годится как справочник:

- **заявки**: `GET /order/for-me` → тап переводит в статус 2 (Принято) →
  «В работу» (3) → до пяти фото через `POST /order-photo/{id}/`,
  комментарий → «Выполнил» (4) или «Проблемы» (5);
- **ТО**: `GET /object/by-mechanic/` → `GET /planned-to/by-object/{id}` →
  матрица двенадцати месяцев → чек-лист шагов → отметка шага с комментарием
  и фото → сохранение.

Разбор целиком, с перечнем того, что выбрасываем и почему, — в архиве.

## Что согласовано с заказчиком

Ответы на заданные вопросы, а не предположения.

**Код подрядчика вливаем в существующий `frontend/`**, отдельным
приложением не оставляем. Один `pubspec`, один клиент API, одна
авторизация, один стиль.

**ТО закрывает механик**, и это сразу считается выполненной работой. Прораб
видит свежие сданные работы лентой и гасит счётчик отметкой «проверил».
Приёмки, блокирующей зачёт, нет.

**Платформы: web + APK для Android, iOS не делаем.** Почти у всех механиков
Android. APK бесплатен: та же кодовая база, тот же CI, ни магазина, ни
ревью. iOS — $99 в год и ревью, вернёмся, только если появятся iPhone.
Запускать на iOS-симуляторе как на инструменте разработки это не запрещает.

**Офлайн нужен полный, включая списки** — связь на объектах рвётся.

**Push пока не делаем.** Вкладка «Уведомления» — список внутри приложения
со счётчиком. Firebase и токены устройств — отдельный этап.

**Начинаем с заявок**, потом ТО: поток заявки известен целиком и не требует
миграций, кольцо замкнётся быстрее.

**Проверяем локально через `make up`**, тестовые данные завожу сам. Прод не
трогаем.

**Цена, названная до начала и остающаяся в силе:** полный офлайн делает APK
основной поставкой, а web — запасным входом. На телефоне локальная база
надёжна; в браузере то же живёт в IndexedDB, и браузер вправе её вычистить
(Safari — после ~7 дней без открытия). Кодовая база одна, но полный офлайн
обещаем только для APK.

## Грабли, которые уже стоили времени

1. **Сессия в тестах без автосброса** (`autoflush=False` в
   `src/session.py`). Правку модели доводить `db_session.flush()`, иначе
   фильтр в SQL считает по старому значению, а ответ — по новому, и тест
   врёт в обе стороны.
2. **`to_timestamp` теряет время суток**: `datetime` — наследник `date`, и
   первая ветка пересобирает дату из года, месяца и дня. Для новых меток
   брать `utc_to_timestamp`. Чинить старую функцию — **отдельное решение**,
   она поменяет даты во всех ответах сразу.
3. **Геттеры пишут посчитанные значения обратно в запись.** `getting_order`
   и `get_acts_facts` починены, но `get_object` и `get_universal_user`
   делают так же. С появлением `updated_at` это двигает метку синхронизации:
   простое чтение выглядит как правка. Трогая геттер — считать в переменные.
4. **`changed_since` не совмещать с `only_open`** ни в одной ручке:
   закрытая запись просто исчезнет из ответа, и телефон не узнает, что она
   закрылась.
5. **Новая ручка ломает снимок контракта** — это напоминание, а не поломка:
   `make openapi-update` и дифф в ревью.

## Чего в бэкенде ещё нет

Синхронизация построена только для заявок и ТО. Для полного офлайна
(«всё целиком, включая списки») не хватает `changed_since` у объектов и
справочников — колонка `updated_at` там уже есть, ручек нет.

За границей мягкого удаления осознанно осталось: **статистика и отчёты
архив считают** (включается в `src/core/archiving.py`), и **старые
сущности** — объект, компания, организация, договор, контактное лицо,
участок — фильтр по умолчанию не получили, это правка вместе с фронтом.

## Как запустить проверку

`make test-db-up` поднимает тестовую БД, `make test` гоняет всё, `make lint`
и `make format` — Ruff, `make openapi-update` пересобирает снимок контракта,
`make vault-check` проверяет имена файлов хранилища. Сейчас **753 теста**
зелёные, линт чистый.

Фронт проверяется локальным Flutter 3.47: `flutter analyze` (2583
замечания, ноль ошибок) и `flutter test test/mechanic` (19 тестов, два
красных — см. долги этапа 1).
