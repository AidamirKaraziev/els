# План - мобильное приложение механика и замыкание процесса

Заказчик принял предыдущий пул работ. Дальше замыкаем **два процесса целиком**:

1. график ТО → задача механику в телефоне → исполнение по регламенту → результат у прораба;
2. заявка диспетчера → задача механику в телефоне → исполнение → результат у прораба.

Сегодня оба разорваны в одном и том же месте: **у механика нет рабочего
инструмента**. Всё остальное звено уже живое.

## Разбор кода Вовы (`frontend/els_mobile/`)

Отдельное Flutter-приложение со своим `.git` (один коммит «initial Commit»),
**21 файл, 4280 строк**, Dart SDK `>=2.19 <3.0`, голый `http`, глобальные
изменяемые переменные, перерисовка через один `StreamController.broadcast()`
и `Timer.periodic(3 сек)`. Уровень — прототип.

**Что там сделано и годится как описание потока:**

- заявки: `GET /order/for-me` → тап переводит в статус 2 (Принято) → «В работу»
  (3) → до 5 фото через `POST /order-photo/{id}/`, комментарий, «Выполнил» (4)
  или «Проблемы» (5);
- ТО: `GET /object/by-mechanic/` → `GET /planned-to/by-object/{id}` → матрица
  12 месяцев → чек-лист шагов из `act_fact.step_list_fact`, отметка шага с
  комментарием и фото, сохранение через `PUT /act-fact/{id}`.

**Что выбрасываем:**

- **приложение вообще не войдёт** — стучится в `POST /api/v1/cp/sign-in/`, а
  этой ручки после рефакторинга авторизации больше нет, только `/auth/login`
  с парой токенов;
- **логин и пароль захардкожены** (`m@mail.ru` / `1111`), поля ввода
  игнорируются; токен не сохраняется, refresh и выхода нет;
- **адрес сервера прибит в коде**: `185.154.193.42:8000` по `http://`
  (`lib/helpers/my_colors.dart:39`) — надо через `dart-define`, см.
  [[настройки фронта - dart-define, а не .env в рантайме]];
- **фото шага ТО кладётся байтовым массивом прямо в текстовое поле БД**;
- **ТО не закрывается**: `finished_at` никто не проставляет, а именно по нему
  считается выполнение графика — [[выполнение считается по дате закрытия акта, а месяц берётся из плана]];
- **нет экрана «мои ТО»**: механик обязан сам вспомнить объект и месяц;
- фото грузятся как `Image.network('http://$photo')` без заголовка — против
  [[картинки грузятся с заголовком, а не по короткоживущей ссылке]];
- профиль правится через админскую ручку `/cp/admin/universal-user/{id}/`.

## Что согласовано с заказчиком

Разбор шёл вопросами, ниже — ответы, это договорённости, а не предположения.

**Код Вовы вливаем в существующий `frontend/`**, отдельным приложением не
оставляем. Один `pubspec`, один клиент API, одна авторизация, один стиль.
Экраны Вовы — справочник по потоку, вёрстка по макету.

**ТО закрывает механик**, и это сразу считается выполненной работой.
Прораб при этом должен видеть свежие сданные работы **нативно** — лентой, —
чтобы проверить, если ему нужно. Приёмки, блокирующей зачёт работы, нет:
прораб только гасит счётчик отметкой «проверил».

**Чек-лист переводим в нормальный формат с миграцией**, фото шага — отдельной
таблицей и ручкой, как фото заявок. Это ровно то, чем заканчивается
[[чек-лист акта хранится питоновским repr, а не JSON]].

**Платформы: web + APK для Android, iOS не делаем.** Почти у всех механиков
Android. APK бесплатен: та же кодовая база, тот же CI, ни магазина, ни
ревью, ни подписи для стороннего распространения. iOS — это $99 в год и
ревью, вернёмся к нему, только если появятся iPhone.

**Офлайн нужен полный, включая списки** — связь на объектах рвётся.

**Push пока не делаем.** Вкладка «Уведомления» из макета — список внутри
приложения со счётчиком. Firebase и токены устройств — отдельный этап, если
заказчик захочет.

**Начинаем с заявок**, потом ТО: поток заявки у Вовы есть целиком и не
требует миграций, кольцо замкнётся быстрее.

**Проверяем локально через `make up`**, тестовые данные завожу сам. Прод не
трогаем.

## Три цены, названные до начала

**1. Полный офлайн делает APK основной поставкой, а web — запасным входом.**
Локальная база на телефоне работает надёжно; в браузере то же самое живёт в
IndexedDB, и браузер вправе её вычистить (Safari — после ~7 дней без
открытия). Кодовая база одна, собирается и в web, и в APK, но полный офлайн
обещаем только для APK.

**2. Для синхронизации не хватает `updated_at`.** Офлайн-клиенту нужно
спрашивать «что изменилось с момента T». Сейчас такого поля нет **ни в одной
модели, кроме дефектных ведомостей** — 1 из 32. Без него телефон качает всё
целиком при каждом выходе на связь. Значит: колонка в `order`, `objects`,
`acts_fact`, `planned_to` плюс миграция. Проду это не мешает — поле
добавляется, ничего не ломая.

**3. `/order/for-me` отдаёт всё за всё время.** Ни пагинации, ни фильтра по
статусу (`backend/src/crud/crud_order.py:201`), а мобилка Вовы дёргает эту
ручку **каждые 3 секунды**. У механика через год это сотни записей в каждом
запросе. Родня уже известной болезни
[[фронт бесконечно долбил бэкенд запросами к all-objects]].

### Этап 0. Фундамент на бэкенде — **пункты 1–3 сделаны**

Весь этап на бэкенде, где есть тесты и `make lint` / `make test`, и он не
зависит ни от одного экрана. Тестов было 636, стало **673**.

1. `/order/for-me`: фильтры `status_id`, `only_open`, `year`+`month`,
   `changed_since` и страницы; без параметров выдача прежняя, порядок —
   свежие сверху. **Сделано**, 13 тестов в `tests/test_api_orders_for_me.py`.
2. `updated_at` в `order`, `objects`, `acts_fact`, `planned_to` + миграция
   `c5f1a8b34e70`, отрепетированная откатом и повторным накатом. Накопленным
   строкам метка проставлена из даты создания, а не `now()`. **Сделано.**
3. Ручка `GET /act-fact/for-me` — плановые ТО механика по
   `act_fact.main_mechanic_id`, с плановым месяцем из графика, объектом и
   счётчиком «сделано N из M». **Сделано**, 10 тестов в
   `tests/test_api_my_maintenance.py`.
4. Новый формат чек-листа: `step_list_fact` как настоящий JSON, фото шага —
   отдельная таблица и ручка загрузки; миграция переносит накопленное.
   **Не начато.** Разбор трёх накопившихся форм уже вынесен в
   `src/services/checklist.py` — миграция сведёт их к одной.
5. «Завершить ТО» механиком: проставляем `finished_at`. **Почти готово с
   прошлых работ** — `PUT /act-fact/{id}/` уже пишет дату и статус, есть
   `tests/test_api_act_fact_finish.py`. Осталось проверить это правами
   механика и дать ему кнопку.
6. Лента прораба: ручка «сданные работы» (закрытые ТО и заявки вместе) и
   отметка «проверил». **Не начато.**

#### Что нашлось попутно

**Отчёты показывали пустой чек-лист по каждому ТО.** Разбор искал форму
шаблона `steplist_tamplate.json` (`step_name`, `substeps`), а оба фронта
пишут другую: словарь с `numberTo`, внутри которого список шагов лежит **ещё
одной строкой**. Формы не совпадали никогда, а тесты закрепляли ту, которой в
базе нет. Разбор теперь общий — `src/services/checklist.py`, 13 быстрых
тестов, — и раздел «выполнено N из M» в отчётах ожил.

**Чтение заявки помечало её изменённой.** `getting_order` писал посчитанные
метки времени обратно в загруженную запись, и ближайший `flush` в той же
сессии сохранял в базу число вместо даты. Пока `updated_at` не было, это
терялось молча; с ним простой показ списка двигал бы метку синхронизации, и
телефон качал бы всё заново при каждом опросе. Функция больше не трогает
запись.

**`to_timestamp` теряет время суток.** `datetime` — наследник `date`, и
первая же ветка собирает дату заново из года, месяца и дня. Для `created_at`
заявки так с самого начала, и никто не замечал. Для метки синхронизации это
негодно, поэтому рядом появился `utc_to_timestamp` — точный и строго обратный
разбору. Чинить ли `to_timestamp` целиком — **отдельное решение**: это
поменяет значения дат во всех ответах сразу.
