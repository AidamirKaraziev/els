# Текущие приоритеты

## Главная задача периода
**Замкнуть рабочий процесс целиком:** график ТО и заявка диспетчера → задача
механику в телефоне → исполнение по регламенту → результат у прораба. Пул
работ по вебу заказчик принял, разорвано ровно одно звено — у механика нет
инструмента. План со всеми этапами и договорённостями:
[[план - мобильное приложение механика и замыкание процесса]].

Мобильный код Вовы разобран (`frontend/els_mobile/`, 4280 строк, в git не
добавлен): поток заявки там есть целиком, но войти приложение не может —
стучится в снесённую ручку `/cp/sign-in/`. Вливаем в единый `frontend/`,
вёрстка по кадрам страницы «Механик | Мобильная версия» в Figma. Решено:
web + APK для Android, iOS не делаем; офлайн полный; push пока нет; ТО
закрывает механик, прораб видит ленту сданных работ. **Ничего ещё не начато
— следующий шаг — этап 0 (фундамент на бэкенде).**

Прежняя главная задача — собрать монорепозиторий и довести фронтовую часть до
сдачи — остаётся фоном: [[фронтенд перешёл ко мне - монорепозиторий и доработка за деньги]],
[[план работ - интеграция фронта и рефакторинг]].

## Перед выкатом авторизации на прод

Порядок проверен по коду 2026-08-13, миграция отрепетирована на копии боевой
базы: [[миграция репетируется откатом и повторным накатом на копии боевой базы]].

- [ ] **Отправить ветку и слить в `main`.** На удалёнке `b222ce7`, локально
      `15af1e8`. CI проверяет пуш только в `main` и `dev`, поэтому ветку
      прогнать через pull request. Пуш в `main` запускает `release.yml`, тот
      кладёт образы в ghcr с тегами `latest` и `sha-<полный хеш>`.
- [ ] **Задать в `.env` на сервере `SECRET_KEY`, `FIRST_SUPERUSER` и
      `FIRST_SUPERUSER_PASSWORD`** — без них бэкенд не стартует. `SECRET_KEY`
      в этой ветке потерял значение по умолчанию (`config.py:31`), а
      `create_super_admin` вызван без `try` и падает на дефолтных значениях.
      Пароль суперадмина — не короче 8 знаков. `SECRET_KEY` задать один раз и
      не менять: раньше он генерировался при каждом старте, и токены умирали
      при любом перезапуске.
- [ ] **Снять дамп базы на сервере** (`pg_dump`). Обратимо не всё: миграция
      сбрасывает пароли администраторам со слабыми паролями, старых хешей нет
      нигде.
- [ ] **Проверить данные до выката**: нет пользователей с пустым email и нет
      email, совпадающих без учёта регистра. На обоих миграция останавливается
      с внятной ошибкой, и `prod-deploy` встанет.
- [ ] **Выкатить** — `make prod-deploy` на сервере. Фронт и бэк едут одним
      стеком, несовместимости между ними быть не может.
- [ ] Предупредить, что все пользователи будут разлогинены.
- [ ] **Предупредить администраторов со слабыми паролями** («1», «123»,
      «admin», «test», «qwerty» и подобные) — миграция сбросит им пароль, их
      `id` появятся в логе бэкенда предупреждением.
- [ ] После выката: вход всеми шестью ролями и профиль с фотографией — обе
      вещи ломаются заметно и сразу.

**Откат.** Миграция идёт одной транзакцией, при сбое база остаётся целой —
откатывать нечего, чинить данные и повторять. Если приложение ведёт себя не
так после успешной миграции: сначала `alembic downgrade -1` (проверено, 0,3
секунды), затем `IMAGE_TAG=sha-<хеш прежнего коммита> make prod-deploy`.
Крайняя мера — восстановление из дампа с `DROP SCHEMA public CASCADE`.
